1970 – 1990S
Waterfall: "Lên Kế Hoạch Mọi Thứ Trước Khi Code"
Năm 1970, Winston Royce xuất bản bài báo mô tả quy trình phát triển phần mềm tuần tự: Requirements → Design → Implementation → Verification → Maintenance. Mô hình Waterfall chỉ chảy một chiều từ trên xuống. Điều thú vị: chính Royce cũng cảnh báo mô hình này có nhiều rủi ro nghiêm trọng.

Waterfall — Khi Nào Hiệu Quả, Khi Nào Thất Bại

✓ Waterfall hoạt động tốt khi…
Phần mềm giao trên đĩa mềm hoặc băng từ — thay đổi sau khi ship cực kỳ tốn kém Yêu cầu phần mềm tương đối ổn định (hệ thống quân sự, ngân hàng lõi) Cần quy trình rõ ràng, tài liệu hóa đầy đủ cho dự án quy mô lớn

✗ Vấn đề cốt lõi
Khách hàng không biết chính xác mình muốn gì cho đến khi thấy sản phẩm chạy Khi phần mềm hoàn thành sau 2–3 năm, yêu cầu đã thay đổi hoàn toàn Sản phẩm trở nên lỗi thời ngay tại thời điểm bàn giao

Kế hoạch chi tiết là cần thiết, nhưng kế hoạch không thể thay đổi là nguy hiểm. Đây cũng là bài học sẽ quay lại khi chúng ta nói về Spec-Driven Development — viết spec tốt không có nghĩa là "đông cứng" spec.

2001 – 2015
Agile: "Thay Đổi Là Bình Thường"
Tháng 2 năm 2001, 17 nhà phát triển phần mềm gặp nhau tại Utah và viết ra Agile Manifesto — một tài liệu chỉ vỏn vẹn 68 từ đã thay đổi toàn bộ ngành phần mềm. Thay vì lên kế hoạch mọi thứ từ đầu, Agile chấp nhận rằng yêu cầu sẽ thay đổi — và xây dựng quy trình xung quanh sự thay đổi đó.

Các Framework Agile Phổ Biến

Scrum
Sprint 2 tuần, Daily standup, Sprint Review & Retrospective. Team tự tổ chức, tập trung giao sản phẩm cuối mỗi sprint.

Kanban
Công việc chảy liên tục qua các cột. Giới hạn WIP (Work In Progress) để tránh quá tải. Tối ưu throughput.

XP / Extreme Programming
Pair programming, Test-Driven Development (TDD), Continuous Integration. Tập trung cực đoan vào chất lượng kỹ thuật.

Agile giải quyết tốt "yêu cầu thay đổi" nhưng tạo ra thách thức mới: Làm thế nào để giao hàng liên tục mà không hy sinh chất lượng? → Câu trả lời dẫn đến DevOps.

2010S – 2022
DevOps & CI/CD: "Tự Động Hóa Mọi Thứ Có Thể"
DevOps là một văn hóa: xóa bỏ bức tường giữa Development và Operations. CI/CD trở thành tiêu chuẩn ngành — mỗi lần commit code, hệ thống tự động build, test, và deploy. Chu kỳ giao hàng từ hàng tháng rút xuống còn hàng giờ.

DevOps — Công Cụ & Đo Lường

Công cụ tiêu biểu
Jenkins · GitLab CI · GitHub Actions — pipeline automation Docker · Kubernetes — container orchestration Terraform · Ansible — infrastructure as code

Google DORA Metrics
Deployment frequency — tần suất deploy Lead time — thời gian từ code đến prod Change failure rate — tỷ lệ lỗi sau deploy Recovery time — thời gian phục hồi sự cố

⚡ Bottleneck vẫn còn đó: Dù CI/CD có nhanh đến mấy, nếu developer mất 3 ngày để viết một feature, pipeline vẫn phải chờ 3
ngày. Bottleneck lớn nhất vẫn là con người viết code — và đây là lúc AI bước vào cuộc chơi.

Tại Sao Vibe Coding Hấp Dẫn Đến Vậy?

Cảm giác "siêu năng lực"
Tạo app hoàn chỉnh trong vài giờ. Prototype nhanh chưa bao giờ dễ đến vậy — không cần setup phức tạp, không cần đọc docs.

Hackathon sôi động hơn
Viết prompt → Nhận code từ AI → Chạy thử → Thấy chạy được → Tiếp tục. Chu kỳ feedback cực ngắn, cực kỳ thỏa mãn.

Phù hợp deadline ngắn
Đồ án ngắn hạn với áp lực deadline thực sự hưởng lợi từ tốc độ này — trong ngắn hạn. Vấn đề chỉ xuất hiện về sau.

Vấn Đề 3: "Final 20% Problem"

80%: Nhanh trong vài giờ

20%: Polish & tích hợp kéo dài

AI có thể build 80% ứng dụng trong vài giờ — nhưng 20% còn lại (edge cases, polish, integration, performance optimization) lại mất thời gian bằng cả dự án trước đây. 15.000 dòng code mà không ai hiểu = cơn ác mộng khi cần sửa.

Vấn Đề 4: Technical Debt Tích Lũy

Triệu chứng điển hình
Naming không nhất quán giữa các file Cùng một vấn đề giải quyết theo 3 cách khác nhau trong 3 file Patterns lẫn lộn không có nguyên tắc Code tối ưu cho "chạy được ngay", không phải "dễ bảo trì"

Khi nào nổ ra?
Tuần 15–20 của đồ án 20 tuần là thời điểm khủng hoảng điển hình — khi cần tích hợp các module, viết test cuối, và demo cho giáo viên. Đây là lúc technical debt tích lũy trở thành thảm họa thực sự.

CHƯƠNG 1.4
Bức Tranh Toàn Cảnh 2026

Spec-Driven Development (SDD)
Triết lý: Đặc tả rõ ràng trước khi code. Phù hợp cho kiến trúc, API, database schema.

Agent-Driven Development (ADD)
Triết lý: AI là collaborator chủ động. Phù hợp cho implementation, testing, deployment.

Hai approach bổ sung cho nhau hoàn hảo → Hybrid Approach là lựa chọn tối ưu.

APPROACH 1
Spec-Driven Development (SDD)
"Vấn đề không phải AI kém, mà là chúng ta đưa cho AI input kém." Nếu bạn viết một specification rõ ràng, chi tiết, và có thể kiểm chứng được, thì AI sẽ tạo ra code chất lượng cao hơn nhiều.

SDD — Nguyên Tắc & Đánh Giá

Nguyên tắc core
Spec là artifact chính, code là sản phẩm dẫn xuất Quy trình: Specify → Plan → Tasks → Implement → Validate Tools tiêu biểu: GitHub Spec Kit, Amazon Kiro

Đánh giá khách quan
✓ Reproducible, quality gates rõ ràng ✓ Team alignment — spec là ngôn ngữ chung ✓ Dễ bàn giao, dễ kiểm tra với giáo viên
△ Overhead viết spec ban đầu △ Nguy cơ over-specification △ Chậm hơn cho task nhỏ và đơn giản

APPROACH 2
Agent-Driven Development (ADD)
"AI đã đủ thông minh để tự làm, chỉ cần chỉ đường đúng." Thay vì viết spec chi tiết, hãy cung cấp context đầy đủ rồi để agent tự lên kế hoạch và thực thi. Human là nhạc trưởng, AI là dàn nhạc.

ADD — Nguyên Tắc & Đánh Giá

Nguyên tắc core
Agent là collaborator, không phải tool bị động Context setup gồm AGENTS.md, constraints, domain knowledge Quy trình: Context Setup → Intent → Agentic Execution → Human Review Tools: Claude Code, Cursor Agent Mode, Codex CLI

Đánh giá khách quan
✓ Nhanh, flexible, linh hoạt với thay đổi ✓ Explore codebase hiệu quả ✓ Xử lý tốt boilerplate và repetitive tasks
△ Context drift khi task dài △ Hallucination, tự ý thay đổi không mong muốn △ Khó kiểm soát với team lớn

⭐ RECOMMENDED
Hybrid Approach: Kết Hợp Tốt Nhất Của Cả Hai
Nguyên tắc cốt lõi: Dùng SDD cho những gì cần ĐÚNG TỪ ĐẦU (kiến trúc, API contracts, data models, security). Dùng ADD cho những gì cần NHANH VÀ ITERATIVE (UI components, business logic, tests, boilerplate).

Hai Tầng Của Hybrid Approach

SDD Layer — Architecture
Kiến trúc hệ thống → Full spec API contracts → Full spec Database schema → Full spec Security constraints → Full spec
Những quyết định này tốn kém nếu sai — phải đúng từ đầu.

ADD Layer — Implementation
UI components → Agent tự do Unit tests → Agent tự do Bug fixing → Agent tự do Boilerplate / scaffold → Multi-agent
Những task này lặp đi lặp lại và dễ kiểm tra — để agent tự do tăng tốc.

Spec ở tầng kiến trúc, Agent ở tầng implementation. Đây là nguyên tắc phân chia trách nhiệm rõ ràng nhất trong Hybrid Approach.

Hybrid không phải là "dùng cả hai lung tung". Đây là framework có nguyên tắc rõ ràng — khi nào cần spec chặt, khi nào để agent tự do.

Hybrid Phù Hợp Cho Nhóm Sinh Viên: 5 Lý Do
Với nhóm 5 người làm đồ án 20 tuần, Hybrid mang lại những lợi ích cụ thể và đo lường được:

1 Spec làm ngôn ngữ chung của nhóm
Khi 5 người cùng code, spec rõ ràng giúp tránh hiểu lầm và code mâu thuẫn giữa các module.
2 Agent tăng tốc viết code
Mỗi thành viên hoàn thành nhiều hơn trong cùng thời gian, đặc biệt khi vừa học vừa làm.
3 Validation gates bảo vệ chất lượng
Spec-based review phát hiện lỗi sớm, trước khi lan sang module khác và trở thành technical debt.
4 Dễ phân công và theo dõi
Mỗi người assign spec + tasks rõ ràng — giáo viên đánh giá đóng góp cá nhân dễ dàng hơn.
5 Chuẩn bị cho career thực tế
SDD và ADD đều là kỹ năng đang được tìm kiếm trên thị trường lao động 2026.
